## 2026-08-15 — Homebrew install-source detection + cask caveats corruption

- **Root cause #1**: `internal/updater/install_source.go`'s `IsHomebrewCaskroomPath` checked whether the *running executable's* symlink-resolved path contained `/Caskroom/`. Real Homebrew Cask `app` stanzas **copy** the `.app` bundle into `/Applications/` (never a symlink into Caskroom), so this check could never succeed for a genuine Homebrew install — `payload.installSource` always fell back to `"manual"` in `AboutModal.tsx`. The pre-existing test suite didn't catch it because its "manual install.sh copy" fixture (`/Applications/Litelens.app/Contents/MacOS/litelens` → `false`) unintentionally documented the exact same path shape a real Homebrew install produces.
- **Fix applied**: `IsHomebrewCaskroomPath` now checks for the *existence of the known Caskroom directory* (`/opt/homebrew/Caskroom/litelens` Apple Silicon, `/usr/local/Caskroom/litelens` Intel) via an injectable `statFn`, independent of the running binary's own path. **MEDIUM (not fixed, reported to user)** — the function's `realPath` parameter is now silently ignored (kept only for call-site/API compatibility), and both call sites still compute `filepath.EvalSymlinks(exe)` beforehand just to pass in a value that's discarded; flagged as a follow-up cleanup opportunity, not a correctness bug.
- **Lesson**: when detecting "was this installed via package manager X," don't infer from the *running binary's* resolved path if the package manager copies rather than symlinks artifacts — check for the package manager's own known install-registry location (Caskroom dir, dpkg status, etc.) instead. Applies to any future install-source detection work (winget, apt) — verify the actual on-disk artifact-placement behavior of the packaging tool before writing a path-substring check.
- **Root cause #2 (regression from the previous fix in this same file)**: `.github/workflows/job-publish-homebrew.yml` writes the generated cask via `cat > tap_repo/Casks/litelens.rb <<RUBY` — an intentionally **unquoted** heredoc (needed so `$VERSION_NO_V`/`$SHA256` shell-expand inside it). A prior fix added literal backtick-wrapped inline-code text (`` `brew update` ``, `` `brew upgrade` ``) to the cask's `caveats` block; bash interpreted those backticks as command substitution inside the unquoted heredoc and silently executed/stripped them, corrupting the published caveats text (confirmed live via the user's `brew info` output).
- **Fix applied**: escaped the backticks (`` \`brew update\` ``, `` \`brew upgrade\` ``) so they render literally while `$VERSION_NO_V`/`$SHA256` expansion keeps working. **Do not quote the heredoc delimiter** (`<<'RUBY'`) as a fix for backtick/special-character issues in this file — that was considered and rejected because it would break the variable substitution the whole cask-generation step depends on. Any future edits to this heredoc's body must escape `` ` ``, `` $ ``, and `` \ `` individually rather than quoting the delimiter.

## 2026-08-15 — About modal open delay (synchronous startup-cost calls in OpenAbout)

- **Root cause**: `App.OpenAbout()` (`internal/app/settings.go`) synchronously called `getAppSizeBytes()` (`filepath.Walk` over the whole macOS `.app` bundle) and `updater.DetectInstallSource()` (shells out to `brew`, up to a 2s subprocess timeout) on *every* About-modal open, blocking the `menu:open-about` event the frontend waits on before rendering `AboutModal.tsx`.
- **Fix applied**: both values are now computed once in `App.Startup()` and cached on the `App` struct (`appSizeBytes int64`, `installSource string`); `OpenAbout()` and `GetInstallSource()` read the cached fields instead of recomputing.
- **MEDIUM** ✅ — moving `updater.DetectInstallSource()` into `Startup()` meant every app launch on a Homebrew install paid up to the same 2s subprocess cost that used to only hit on About-modal open. Fixed by running `DetectInstallSource()` in a background goroutine started from `Startup()`; the result is written to `a.installSource` under `a.mu` (existing `sync.RWMutex`), and `GetInstallSource()`/`OpenAbout()` now read it under `a.mu.RLock()`. If read before the goroutine finishes, callers just see the zero-value `""`, which the frontend (`AboutModal.tsx`) already renders as "no install-source suffix" — no crash/undefined behavior. This also resolved the sibling MEDIUM about `installSource` not being mutex-guarded, since it's now a genuinely concurrently-written field and correctly covered by `mu`.
- **HIGH** ✅ (found on follow-up startup-delay review, not part of the original About-modal report) — `resolveLoginShellPATH` (`internal/app/shell.go`) was called synchronously in `App.NewApp()`, which runs *before* `wails.Run()` in `main.go` — so on macOS the entire process blocked on spawning a login shell (`$SHELL -l -c "echo $PATH"`, up to a 5s timeout) before the app window could even appear. This was the dominant startup-delay contributor, larger than the `brew` subprocess call above. Fixed by wrapping the call in `go resolveLoginShellPATH(s.ShellPath)`. Safe to background: the function is already best-effort (skips `os.Setenv` and logs on failure/timeout, app keeps the original PATH), and its only consumer (exec-credential-plugin lookups like `aws`/`gcloud` during a later `Connect()`) requires user interaction first, giving the goroutine ample time to finish. No new shared-state guarding needed since `os.Setenv`/`os.Getenv` are already safe for concurrent use.
- **Lesson**: when reviewing "app startup is slow," check every synchronous call reachable from `NewApp()` and `Startup()` for subprocess exec / filesystem walk / network I/O — `NewApp()` runs before `wails.Run()`, so anything blocking there delays the window appearing at all, not just a later in-app interaction. `resolveLoginShellPATH`, `getAppSizeBytes`, and `DetectInstallSource` were all missed by earlier reviews that only looked at the specific reported symptom (About modal) rather than the full startup call graph.
- **MEDIUM (not fixed, reported to user, scope narrowed)** — `appSizeBytes` is still computed synchronously in `Startup()` (plain field, not mutex-guarded) since it wasn't the flagged startup-delay complaint and `filepath.Walk` over the `.app` bundle is typically much faster than the `brew` subprocess call. If it's ever observed to meaningfully slow launch, apply the same background-goroutine + mutex pattern used for `installSource`.
- **Lesson**: when a Wails-bound method fires on user interaction (menu click, modal open) and does anything beyond map/string construction — filesystem walks, subprocess exec, network calls — check whether the underlying value is static for the process lifetime and can be cached once in `Startup()` instead of recomputed per-call. Applies to any future "on-demand" Go method that turns out to wrap an expensive deterministic computation.

## 2026-08-12 — UI hang on detail-drawer open after connecting to large cluster

- **Root cause**: All ~30 K8s informers (`internal/kube/informers.go:58`) share one 30s `SharedInformerFactory` resync period, so they periodically fire near-simultaneous emit bursts. Each `emitXxx(namespace)` handler did a redundant second `ListXxx(lister, namespace)` (full relist + DTO reconversion) after already listing cluster-wide, and `emitPodsWithMetrics` additionally blocked the whole emit on a synchronous metrics-server HTTP call (`metricsFetchTimeout = 3s`, `internal/app/app.go:25`) before emitting anything. On the frontend, every pushed Wails event applied `setState` synchronously with no priority, and `DeploymentDetailDrawer`'s tab derivations re-filtered/re-sorted on every unrelated array replacement — so a resync-boundary collision with drawer-open produced a burst of large, unprioritized, non-memoized re-renders that blocked the main thread (unclickable UI for several seconds).
- **Fix applied** (no CRITICAL/HIGH from Phase 5 review): namespace-scoped emit branches in `internal/app/{pod,deployment,daemonset,replicaset,statefulset}.go` now filter the already-fetched cluster-wide slice in memory instead of re-listing; `pod.go`'s `emitPodsWithMetrics` emits pods immediately and fetches/applies metrics in a background goroutine (reusing the captured `allPods` slice, not re-listing) before re-emitting. Frontend `use{Pods,Deployments,DaemonSets,ReplicaSets,StatefulSets}UpdateEvents.ts` wrap their event-driven `setState` in React 19 `startTransition` so background pushes are deprioritized below user interactions like clicks. `DeploymentDetailDrawer.tsx`'s `DeploymentOverviewTab`/`DeploymentPodsTab` derivations are now `useMemo`'d.
