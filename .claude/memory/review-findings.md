## 2026-08-27 — Helm releases leaked stale/wrong-cluster namespace filter on reconnect-to-same-context

- **Symptom (user report)**: on first opening the app and viewing minikube's Helm Releases, `activeNamespaces` excluded `default` in the UI dropdown, but the table still showed releases from `default` (in fact from all namespaces). Switching to `docker-desktop` still showed minikube's full release list.
- **Root cause**: `Connect()` (`internal/app/app.go`) reset `a.activeNamespaces = nil` on every call, but only pushed that reset to plugins via `a.emitActiveNamespacesToPlugins(nil)` when `contextChanged` was true (a genuine cluster switch). A plain reconnect to the *already-active* context — which happens on a frontend/browser reload while the Go host process keeps running — left `contextChanged` false, so neither a reset nor the correct restored filter was ever pushed to the Helm plugin subprocess. The plugin kept whatever namespace filter it last synced (stale, possibly from a previous session/cluster), while the frontend's own async restoration of persisted defaults (`MainLayout.tsx`'s `useGetDefaultNamespaces` → `setActiveNamespaces` on mount) raced against — and often lost to — the plugin's business calls, whose results TanStack Query then cached indefinitely (`placeholderData: keepPreviousData`, no invalidation).
- **Fix applied**: `Connect()` now always restores the context's persisted default namespace filter (`config.Settings.ClusterDefaultNamespaces[contextName]`, via new helper `App.restoredNamespacesForContextLocked` in `internal/app/utils.go`, which returns a defensive copy so `a.activeNamespaces` never aliases the settings-backed slice) and unconditionally calls `a.emitActiveNamespacesToPlugins(restoredNamespaces)` — synchronously within `Connect()`, before it returns to the frontend — regardless of whether it's a genuine context switch or a reconnect to the same context. The `contextChanged` variable and its conditional gate were removed entirely (confirmed via grep it had no other use).
- **Process note — initial false lead**: an earlier session in this same investigation suspected the bug was already fixed and remaining symptoms were just stale-process/test artifacts. A clean repro (fresh browser reload + fresh reconnect) disproved this — the real defect was still live. Separately, mid-fix, `wails dev`'s hot-reload rebuilt the host binary on save but did **not** restart the already-running (orphaned, `PPID=1`) Helm plugin subprocess, which briefly masked the fix during live QA until the stale subprocess was manually killed to force a relaunch. **Lesson: when live-QA'ing a plugin-host IPC fix under `wails dev`, verify the plugin subprocess's own start time/PID is newer than the fix, not just the host binary's — `ps -o pid,ppid,lstart,command` on the plugin process name.**

- **Verified**: `go build ./...`, `go vet ./...`, `go test -race -count=1 ./internal/...` (all 10 packages pass), `pnpm lint:be` (staticcheck clean for root + `packages/core`), `pnpm format` (no changes needed).

## 2026-08-25 — Pods multi-namespace filter dropped namespaces without live push events

- **Root cause**: `useGetPods.ts`'s merge logic did `if (latestPods.length) baseData = filterByNamespaces(latestPods, namespaces)` — a wholesale override of the correct initial `query.data` (from `ListPods(namespaces)`, covering all selected namespaces) as soon as ANY selected namespace received a live push event via `usePodsUpdateEvents`. That hook's `latestPods` only ever contains entries for namespaces that have already received at least one `pods:{ns}:update` event (backend only emits per-namespace events for namespaces with actual pod churn, e.g. `internal/app/pod.go`'s `a.emitPods([]string{namespace})`). Selecting 4 namespaces where only 2 had recent churn meant the other 2 vanished from the table the moment any event arrived.
- **Fix applied**: `usePodsUpdateEvents.ts` now returns `{ pods: Pod[]; liveNamespaces: Set<string> }` instead of a bare array — `liveNamespaces` tracks which namespaces have received at least one live event (reset when the namespace selection changes). `useGetPods.ts` merges per-namespace: keeps `query.data` for namespaces absent from `liveNamespaces`, uses `latestPods` for namespaces present in it, then filters by the selected namespaces. `useGetPodDetail.ts`/`useGetPodYAML.ts` updated for the new return shape (no behavior change, they don't use `liveNamespaces`).
- **Rejected first draft**: an initial fix derived "namespaces with live data" from `latestPods.map(p => p.Namespace)` instead of a separate tracked set. Phase 2 review caught that this can't distinguish "no event yet" from "event arrived with an empty array" (e.g. all pods in a namespace were deleted) — the empty-array case would fall through to stale `query.data` and resurrect deleted pods in the UI. The `liveNamespaces` Set (populated on every event regardless of payload emptiness) fixes this.
- **MEDIUM (not fixed, accepted)** — `usePodsUpdateEvents.ts`'s namespace-change detection runs in the render body (`if (JSON.stringify(prevNamespaces) !== JSON.stringify(namespaces))` calling `setState` directly) rather than in a `useEffect`; works correctly under React 18+ batching but is a fragile pattern. Pre-existing before this fix, not introduced by it.
- **MEDIUM (not fixed, accepted)** — no direct unit test exercises `useGetPods.ts`'s merge logic itself (multi-namespace-partial-events and empty-array-no-resurrection scenarios are only verified by code trace / the underlying `usePodsUpdateEvents` tests, not an integration test of the merge).
- **Scope note for future work**: other resource modules (Deployments, DaemonSets, etc.) still use the older wholesale-override merge pattern (`if (latestX.length) baseData = filterByNamespaces(latestX, namespaces)`) and likely have the same latent bug for multi-namespace selection — out of scope for this fix (pods-only per the reported issue), but worth the same `liveNamespaces` treatment if reported there too.

## 2026-08-25 — Follow-up #2: re-enabling a plugin after disable didn't restore its nav entry until reload

- **User caught this live again**: after the 2026-08-25 entry above fixed teardown-on-disable/remove, the user reported the opposite direction — disable Helm, then re-enable it, and the nav entry (and its other registrations) did NOT come back until a full FE reload.
- **Root cause**: the browser's ES module loader caches an evaluated module by exact URL string for the page's lifetime. `PluginResourceView.tsx` computes its dynamic `import()` URL as `/api/plugins/<id>/dist/index.js?v=<bundleChecksum-prefix>`; `bundleChecksum` only changes on plugin reinstall/update, not on a disable→re-enable toggle, so the URL on re-enable is byte-identical to the one already imported earlier in the session. `import()` on an already-seen URL returns the cached, already-evaluated module instantly WITHOUT re-running its top-level code — and a plugin bundle's `registerNavEntry()`/`registerViews()`/`registerTrayFamilies()`/`registerEvents()`/`registerStylesheets()` calls are side effects of that top-level module-eval. React remounting `PluginResourceView` cannot force re-evaluation; only a different URL or a full page reload can.
- **Rejected approach**: appending a random per-mount nonce to the import URL to force cache-busting. This broke `PluginResourceView.test.tsx`, which mocks plugin bundles via `vi.mock("<exact literal URL>", ...)` — a runtime-random URL no longer matches the test's static mock specifiers. Also generally fragile: couples correctness to browser module-cache internals rather than to something the app actually owns.
- **Fix applied**: snapshot-and-restore, new module `frontend/src/app/clusters/plugins/pluginAssetSnapshot.ts`. `capturePluginAssetSnapshot(pluginId, bundleChecksum)` reads whatever the five registries hold for a plugin right after its first successful `import()` and stores it keyed by `pluginId`+`bundleChecksum`. `restorePluginAssetSnapshot(pluginId, bundleChecksum)` re-populates the registries directly from that snapshot instead of re-importing. `PluginResourceView.tsx`'s `lazy()` factory now tries `restorePluginAssetSnapshot` first and only falls through to `import(pluginAssetUrl)` + `capturePluginAssetSnapshot` when nothing matches — never touches the import URL, so it doesn't fight the browser cache and the existing literal-URL-mock test suite needed no changes. Required adding `getHandlersForPlugin(pluginId)` to `pluginEventRegistry.ts` (existing `getHandler` only looked up by event name, not by plugin).
- **Verified live**: installed Helm on minikube, disabled from Marketplace, re-enabled, navigated back to the cluster view without reloading — Helm nav group + Charts/Releases sub-entries reappeared immediately, and clicking into Charts rendered the full 272-item chart list (not just the nav label with a broken view).
- **Process lesson**: this is the second follow-up this session for the same feature area, and both prior "fixed" states passed unit tests and Phase 5 static review. Registry/lifecycle bugs tied to browser-specific caching or component mount/unmount timing are structurally invisible to Read/Grep-only review and often invisible to jsdom-based unit tests too (jsdom's module loader doesn't reproduce the browser's per-URL eval-once caching the same way) — live browser round-trips are not optional for this class of fix, they're the only verification method that actually exercises the bug.

## 2026-08-24 — Helm plugin "backend unreachable" on fresh install (follow-up to 2026-08-22 entry below; root cause now proven)

- **Root cause found** (the 2026-08-22 entry below predicted exactly this would be needed): `internal/plugin/loader.go`'s `IsAlive()` is deliberately PID-only (comment at ~loader.go:282-286) — it cannot detect a subprocess that's alive but whose HTTP listener never bound or died internally (a startup-timing race right after the plugin prints its READY handshake). `internal/app/plugin.go`'s `GetPluginBackendAddr` only relaunched when `!IsAlive()`, so an alive-but-unresponsive process was returned forever — the helm plugin's own frontend bundle (`build/storage/plugins/helm/dist/chunk-PWBDKZDJ.js`, compiled from a separate repo) retries once by re-asking Go for an address, but Go returned the *same* stale address both times since it had no way to know the HTTP server was dead. Surfaced as the literal string `"Plugin backend unreachable"`, which lives in that plugin-frontend bundle, not host code — **when grepping for a plugin error string, check the plugin's own bundle under `build/storage/plugins/<id>/dist/` too, not just host Go/TS.**
- **Fix applied**: `GetPluginBackendAddr` now does a fast `net.DialTimeout` (1s) TCP health check before returning an address; on failure it calls `loader.Shutdown()` (required — otherwise `Launch()`'s stale-lock-file-reuse path just reuses the same dead PID) then `loader.Launch()` to force a clean relaunch, then re-dials once before giving up. Two misleading comments in `loader.go` claiming "the frontend's on-demand retry path" catches an alive-but-unresponsive process were corrected — traced and confirmed false (the frontend retry never triggers a Go-side relaunch, it just re-reads the same stale port).
- **Process note**: this pipeline's Phase 1 needed 2 re-investigation rounds — round 1's theory (`GetContextKubeconfigPath` returning an error) was rejected by Phase 2 review because that function never returns an error for a missing context (`internal/app/settings.go:~251` returns `("", nil)`); round 2's correct theory only surfaced once the orchestrator read the plugin's own compiled frontend bundle directly, which the architect subagent hadn't checked in either round. **Lesson: for a plugin-surfaced error message, locate the literal string first** (grep across host code AND `build/storage/plugins/*/dist/*`) before theorizing about host-side causes.
- **MEDIUM (not fixed, accepted)** — two simultaneous `GetPluginBackendAddr` callers hitting a dead listener each independently call `Shutdown()`+`Launch()`; `loader.mu` serializes this safely (no correctness bug) but can launch the plugin subprocess twice when once would suffice.
- **MEDIUM (not fixed, accepted)** — the shutdown-before-relaunch error is logged via `fmt.Printf` rather than the project's logger, for consistency with existing `Launch()`-adjacent logging in the same file; flagged as a stylistic follow-up only.

## 2026-08-15 — Homebrew install-source detection + cask caveats corruption

- **Root cause #1**: `internal/updater/install_source.go`'s `IsHomebrewCaskroomPath` checked whether the *running executable's* symlink-resolved path contained `/Caskroom/`. Real Homebrew Cask `app` stanzas **copy** the `.app` bundle into `/Applications/` (never a symlink into Caskroom), so this check could never succeed for a genuine Homebrew install — `payload.installSource` always fell back to `"manual"` in `AboutModal.tsx`. The pre-existing test suite didn't catch it because its "manual install.sh copy" fixture (`/Applications/Litelens.app/Contents/MacOS/litelens` → `false`) unintentionally documented the exact same path shape a real Homebrew install produces.
- **Fix applied**: `IsHomebrewCaskroomPath` now checks for the *existence of the known Caskroom directory* (`/opt/homebrew/Caskroom/litelens` Apple Silicon, `/usr/local/Caskroom/litelens` Intel) via an injectable `statFn`, independent of the running binary's own path. **MEDIUM (not fixed, reported to user)** — the function's `realPath` parameter is now silently ignored (kept only for call-site/API compatibility), and both call sites still compute `filepath.EvalSymlinks(exe)` beforehand just to pass in a value that's discarded; flagged as a follow-up cleanup opportunity, not a correctness bug.
- **Lesson**: when detecting "was this installed via package manager X," don't infer from the *running binary's* resolved path if the package manager copies rather than symlinks artifacts — check for the package manager's own known install-registry location (Caskroom dir, dpkg status, etc.) instead. Applies to any future install-source detection work (winget, apt) — verify the actual on-disk artifact-placement behavior of the packaging tool before writing a path-substring check.
- **Root cause #2 (regression from the previous fix in this same file)**: `.github/workflows/job-publish-homebrew.yml` writes the generated cask via `cat > tap_repo/Casks/litelens.rb <<RUBY` — an intentionally **unquoted** heredoc (needed so `$VERSION_NO_V`/`$SHA256` shell-expand inside it). A prior fix added literal backtick-wrapped inline-code text (`` `brew update` ``, `` `brew upgrade` ``) to the cask's `caveats` block; bash interpreted those backticks as command substitution inside the unquoted heredoc and silently executed/stripped them, corrupting the published caveats text (confirmed live via the user's `brew info` output).
- **Fix applied**: escaped the backticks (`` \`brew update\` ``, `` \`brew upgrade\` ``) so they render literally while `$VERSION_NO_V`/`$SHA256` expansion keeps working. **Do not quote the heredoc delimiter** (`<<'RUBY'`) as a fix for backtick/special-character issues in this file — that was considered and rejected because it would break the variable substitution the whole cask-generation step depends on. Any future edits to this heredoc's body must escape `` ` ``, `` $ ``, and `` \ `` individually rather than quoting the delimiter.

## 2026-08-15 — About modal open delay (synchronous startup-cost calls in OpenAbout)

- **Root cause**: `App.OpenAbout()` (`internal/app/settings.go`) synchronously called `getAppSizeBytes()` (`filepath.Walk` over the whole macOS `.app` bundle) and `updater.DetectInstallSource()` (shells out to `brew`, up to a 2s subprocess timeout) on *every* About-modal open, blocking the `menu:open-about` event the frontend waits on before rendering `AboutModal.tsx`.
- **Fix applied**: both values are now computed once in `App.Startup()` and cached on the `App` struct (`appSizeBytes int64`, `installSource string`); `OpenAbout()` and `GetInstallSource()` read the cached fields instead of recomputing.
- **MEDIUM** ✅ — moving `updater.DetectInstallSource()` into `Startup()` meant every app launch on a Homebrew install paid up to the same 2s subprocess cost that used to only hit on About-modal open. Fixed by running `DetectInstallSource()` in a background goroutine started from `Startup()`; the result is written to `a.installSource` under `a.mu` (existing `sync.RWMutex`), and `GetInstallSource()`/`OpenAbout()` now read it under `a.mu.RLock()`. If read before the goroutine finishes, callers just see the zero-value `""`, which the frontend (`AboutModal.tsx`) already renders as "no install-source suffix" — no crash/undefined behavior. This also resolved the sibling MEDIUM about `installSource` not being mutex-guarded, since it's now a genuinely concurrently-written field and correctly covered by `mu`.
- **HIGH** ✅ (found on follow-up startup-delay review, not part of the original About-modal report) — `resolveLoginShellPATH` (`internal/app/shell.go`) was called synchronously in `App.NewApp()`, which runs *before* `wails.Run()` in `main.go` — so on macOS the entire process blocked on spawning a login shell (`$SHELL -l -c "echo $PATH"`, up to a 5s timeout) before the app window could even appear. This was the dominant startup-delay contributor, larger than the `brew` subprocess call above. Fixed by wrapping the call in `go resolveLoginShellPATH(s.ShellPath)`. Safe to background: the function is already best-effort (skips `os.Setenv` and logs on failure/timeout, app keeps the original PATH), and its only consumer (exec-credential-plugin lookups like `aws`/`gcloud` during a later `Connect()`) requires user interaction first, giving the goroutine ample time to finish. No new shared-state guarding needed since `os.Setenv`/`os.Getenv` are already safe for concurrent use.
- **Lesson**: when reviewing "app startup is slow," check every synchronous call reachable from `NewApp()` and `Startup()` for subprocess exec / filesystem walk / network I/O — `NewApp()` runs before `wails.Run()`, so anything blocking there delays the window appearing at all, not just a later in-app interaction. `resolveLoginShellPATH`, `getAppSizeBytes`, and `DetectInstallSource` were all missed by earlier reviews that only looked at the specific reported symptom (About modal) rather than the full startup call graph.
- **MEDIUM (not fixed, reported to user, scope narrowed)** — `appSizeBytes` is still computed synchronously in `Startup()` (plain field, not mutex-guarded) since it wasn't the flagged startup-delay complaint and `filepath.Walk` over the `.app` bundle is typically much faster than the `brew` subprocess call. If it's ever observed to meaningfully slow launch, apply the same background-goroutine + mutex pattern used for `installSource`.
- **Lesson**: when a Wails-bound method fires on user interaction (menu click, modal open) and does anything beyond map/string construction — filesystem walks, subprocess exec, network calls — check whether the underlying value is static for the process lifetime and can be cached once in `Startup()` instead of recomputed per-call. Applies to any future "on-demand" Go method that turns out to wrap an expensive deterministic computation.

## 2026-08-21 — Multi-namespace filter showing unfiltered results on initial render

- **Root cause**: `getEffectiveNamespace()` (`frontend/src/app/clusters/shared/utils/namespaceFiltering.ts`) collapses a multi-namespace selection (>1 namespace) to `""` (cluster-wide fetch), since the backend only supports single-namespace or all-namespace queries.
